## Проверка кода клиента

Разобрана копия 32-битного `Wow.exe`, SHA-256 `99155d4d6ed4937a5ab1f5972d11e8605b986561b9f08686ab66af2c582194ec`. Это проверка конкретного exe; выводы не переносятся автоматически на `WowClient64.exe` или другие сборки.

Наблюдения по дизассемблированию (VA):

- `0x006AE900`: копирует BLP2-заголовок/палитру во внутренний объект; количество mip-уровней берёт через `0x006AB700` из размеров и флага, а не считает все ненулевые offsets.
- `0x006AB700`: конечный цикл деления размеров до 1; отдельно распознаёт развёртку width == 6*height.
- `0x006AB760`: размещает mip-pointer table перед выровненным хранилищем пикселей, исходя из числа уровней по размерам.
- `0x006B00FF..0x006B012C`: fast path прямого представления данных идёт по sizes до нуля и записывает указатели без проверки индекса по вычисленному числу уровней.
- `0x006B00AC..0x006B00E7`: другой путь декодирования имеет явную границу по вычисленному количеству уровней.

Различие границ — реальное основание для hardening. Оно само по себе не доказывает выход за весь выделенный heap-блок: рядом с таблицей есть выравнивание и хранилище пикселей. Бесконечный цикл и причина сильного падения FPS остаются неподтверждёнными.

## Native-проверка и прототип исправления в памяти

Из копии exe извлечены 350 байтов функции `0x006AFFD0..0x006B012D`; SHA-256 фрагмента `f74ce8ec7778092011d97da5cd9b8e3a38347cd7aead0fbfaf6da05dbe318409`. Фрагмент выполнен в отдельном x86-стенде на ветке прямых mip-указателей, без загрузки/запуска игры. До исполнения проверялись хэши exe и фрагмента. В DLL игровой код не добавлялся.

На всех 30 текстурах проверены исходный вариант и вариант с обнулёнными хвостовыми offset/size только во внутренней копии заголовка. O0 и O2 с включёнными assert прошли. У четырёх текстур исходная функция записала на один указатель больше runtime-числа уровней; после обнуления хвоста таких записей нет. Указатели всех действующих mip-уровней бит-в-бит те же, исходные байты BLP остаются неизменными. На этих тестах исходная функция тоже завершилась, зависания не наблюдалось.

Это первая проверка конкретного fast path и образцов, не полный игровой прогон или подтверждение FPS-эффекта. Реализованная затем защита описана ниже.

## Вариант через d3d9.dll без изменения EXE и MPQ

Стандартный D3D9 API не даёт исходный BLP-заголовок. `IDirect3DDevice9::CreateTexture` получает размеры, количество уровней и формат, а Northlight в `src/proxy/renderer.cpp` сейчас передаёт эти параметры backend и оборачивает ресурс. Ограничение `Levels` там не исправит обход внутренней таблицы BLP-указателей в клиенте. Шейдер также не управляет этим CPU-кодом. Сигнатура API: [Microsoft CreateTexture](https://learn.microsoft.com/en-us/windows/win32/api/d3d9/nf-d3d9-idirect3ddevice9-createtexture).

Реализовано в `src/proxy/blp_mip_guard.h` и подключено в `backend()` из `src/proxy/renderer.cpp`, перед загрузкой графического runtime и вне DllMain. Вместо отдельного callback на каждую загрузку DLL однократно заменяет **47 байтов** существующего fast path собственным ограниченным циклом. Он останавливается по первому нулевому size либо после `min(внутреннее число уровней клиента, 16)` записей. Заголовок и пиксели BLP при этом вообще не изменяются. Все переходы остаются внутри клиентской функции; защита не хранит указателей на код Northlight.

Перед записью проверяются fixed-base x86 PE32 и SHA-256 трёх фрагментов: функции прямого представления (350 байт), разбора заголовка (144) и вычисления числа mip-уровней (96). Для уже установленного идентичного ограниченного цикла предусмотрено `already-active`. Несовпадение подписи, layout или чужой перехват оставляют код без изменений. Оригинальные инструкции клиента в production DLL не встроены: сохранённые при установке байты существуют только в памяти для проверки и отката.

Установка использует предварительную перепись потоков и native-итератор текущего процесса. Остальные потоки временно останавливаются; их PC проверяется на попадание в заменяемый участок. Если он занят, поток недоступен, перепись изменилась или исчерпан предел 1024 потоков, попытка прекращается. Пока потоки остановлены, нет выделений heap, журналирования, загрузки DLL или захвата пользовательских блокировок. Перед записью повторно сравнивается весь сохранённый фрагмент. Ошибка публикации/восстановления защиты страницы вызывает откат точных исходных байтов перед возобновлением потоков. Не меняются счётчики приостановки, которыми владел вызывающий код.

По умолчанию включено. В `northlight-renderer.ini`, секция `[Renderer]`, `BlpMipGuard=0` отключает установку при следующем запуске клиента; изменение INI не отменяет уже выполненную установку в текущем процессе. Диагностика: `BLP mip guard status=active` / `already-active` либо конкретная причина отказа. Для imported-replay сборки запись в клиентский код отключена. Дополнительных файлов MPQ и изменений Wow.exe на диске нет.

### Проверки реализации

- `tests/test_blp_mip_guard.py` зарегистрирован в `tests/discovery.txt`; его обычный запуск не требует клиентских файлов или GPU. O0/O2, assert включены, `-Wall -Wextra -Werror`.
- 374 сочетания runtime-count 0..20/UINT32_MAX и длины префикса sizes 0..16, включая полностью заполненную таблицу. За последней разрешённой записью находится PAGE_NOACCESS. Проверяются неизменность payload и нетронутые выходные ячейки.
- Ошибки VirtualProtect/FlushInstructionCache инъецируются в стенде; проверяются откат байтов и восстановление RX. Отдельный поток внутри заменяемого цикла приводит к `decoder-busy`; исходный код сохраняется. Проверены приостановленный вызывающим кодом поток и параллельная активность heap на шести потоках.
- При явном `--client` стенд читает только локальную копию exe и копирует **три проверяемых фрагмента** в зарезервированное хранилище собственного тестового PE. Клиентские entrypoint/imports/инициализация игры не исполняются. Адреса обеспечивает собственная BSS-секция теста; ASLR отключается только у скомпилированного тестового exe. API Windows не подменяются.
- На 30 настоящих BLP корабля у четырёх устранена запись лишнего указателя. Смещения всех действующих mip-указателей совпадают с исходной функцией, исходные байты BLP не меняются. Только 47 ожидаемых байтов в зарезервированной области стенда отличаются после установки.
- 171 сочетание размеров/флага mipmaps: NPOT, обычные цепочки, отсутствие mipmaps и cube strip 6*height. Исполняется также исходная функция вычисления количества уровней. Проверяются допустимые и недопустимые firstLevel/LOD.
- Production `frd9.dll` проверена в том же собственном процессе через обычный `Direct3DCreate9`: O0/O2 стенды, DXVK 2.7.1 и 3.1.1, по три цикла API/устройства. Установка действительно выполняется до возврата API. Четыре mip-уровня A8R8G8B8 проходят byte-exact roundtrip; очистка render target и GPU-readback дают ровно ожидаемые пиксели. Сторонние подсистемы могут удерживать production proxy после FreeLibrary; это записано как `proxyResident=1`, а не выдано за фактическую выгрузку.
- `tests/blp_mip_guard_module.cpp` отдельно собирает тот же установщик в минимальную DLL: подтверждены её полная выгрузка (`moduleResident=0`) и последующее исполнение исправленного клиентского кода на всех 30 образцах.

Native D3D9 на RTX 4090 сообщил INTZ=1, RESZ=0, floatRT=1, SM3=1 и был отклонён существующей проверкой возможностей Northlight (это диалог на присланном скриншоте). Этот GPU-вариант не засчитывается как PASS. Проверки успешно завершены на обоих DXVK с RESZ=1.

Production DLL **0.3.217** собрана штатным `python scripts/build_renderer.py`, прошла `build_packages.check_dll`; размер 9,093,120 байт, SHA-256 `fe5a7cfa11e3a492176520ccc7dc012cfe618902b970f85d32a31067a8b310fa`, source identity `547595df8094837b3c879a9bff2df1a0790ecb8cff6f0db867ea8ff7681ee5bc`. В игру не устанавливалась. Пять связанных зарегистрированных проверок прошли; три первоначально запрошенных host-tool проверки пропущены из-за отсутствия clang++/lldb/objdump и не засчитываются как PASS.

Это защита конкретного BLP-цикла. Полный игровой прогон, достаточная ранность для всех возможных путей загрузки и влияние на FPS ещё не подтверждены. Она не исправляет произвольные повреждения пикселей/моделей и не уменьшает объём HD-ассетов. MPQ-overlay и правка файла Wow.exe не реализуются.

## Что сделает текущий инсталлер

Выполнены только read-only `gather_inputs -> step_digests -> plan` из `scripts/install_world_cache.py`. План видит девять новых архивов и назначает `mode=full`: пересобрать геометрию Azeroth/Kalimdor/Expansion01/Northrend и lights/fog/celestial. Текущий cache был собран до добавления этих архивов.

Полная установка приведёт статические данные Northlight в соответствие с новыми моделями/текстурами, но текущий код инсталлера **не нормализует BLP в исходных MPQ**. Его scene builder создаёт собственные FGS-материалы; оригинальный загрузчик WoW продолжает читать оригинальные BLP. Такой прогон не является проверенным исправлением рассматриваемой проблемы.

Автоматическую совместимость можно делать отдельным этапом инсталлятора: аудит, нормализация только проверенных случаев, проверка неизменности действующих уровней, затем transactional installation с восстановлением. Вариант с override-архивом сохраняет оригинальные паки, но обычные MPQ-файлы потребуют копирования полного payload исправленных BLP; это не маленький patch из одних заголовков. Встраивание в существующий art layer также требует учесть архивный приоритет и чужой patch-z. Прямое переписывание A..S нельзя выдавать за обычную пересборку cache.
