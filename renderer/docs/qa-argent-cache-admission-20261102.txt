ArgentTournamentDungeon: исправление допуска replay GPU cache, 2026-11-02

Исправлено в WorldRenderer::uploadReplay. Раньше первая новая резидентная
геометрия в кадре проверялась как рост на 64 МиБ, а результат разрешал или
запрещал все остальные заявки. dynamicBudget требовал available=448 МиБ и
largest=144 МиБ. В QA при largest=79 МиБ это запрещало даже малые меши.

GPU-замеры и указанная ниже исследовательская DLL относятся к полному
локальному интегрированному дереву с уже существовавшими правками. Само
исправление допуска, его регрессии и стенд публикуются отдельно от этих
посторонних локальных изменений; identity DLL не является identity чистого PR.

Теперь перед каждой заявкой проверяется суммарный объём допущенных мешей
этого вызова uploadReplay плюс один stride на меш для выравнивания общего
пакета. Ожидающие commit меши ещё не отражены в измеренной свободной памяти,
поэтому проверка только текущего bytes была бы недостаточна. Созданные и
неудачные допущенные заявки не вычитаются из накопленного резерва: это
консервативная оценка до следующего вызова. Новая проверка получает свежие
GlobalMemoryStatusEx/VirtualQuery данные через существующий admission probe.
Готовая резидентная геометрия проверку роста не вызывает.

Сохранены ProcessReserve=256 МиБ, тройной запас объёма, двойной запас
непрерывного блока плюс ChunkMargin=16 МиБ, лимиты кэша и загрузки, probation,
ограничение времени создания и обычный bulk fallback. Отказ опасной аллокации
и возврат необязательного кэша перед ростом bulk-буферов остались прежними.
Изменение не увеличивает общий лимит кэша и не меняет качество теней.

Регрессионная проверка

test_replay_upload.py исполняет извлечённый production uploadReplay с четырьмя
кэшами: старый отдельный, старый batched с multi-/single-stream и текущий
NativeStore/NativeClient. Каждый — O2 и ASan+UBSan. Новый случай упал на
старом коде при 942/79 МиБ; после изменения все восемь вариантов проходят.
Проверены накопленные заявки, случай «хватает только на первый меш», сброс
резерва в следующем вызове, недостоверная проба памяти, недостаток aggregate/
contiguous VA, сохранность draw/байтов, отказы создания и COM-владение.

Linux CPU runner: 6 PASS, 0 FAIL. test_shared_gpu_wiring.py в нём был SKIP
из-за Windows/zig требований, затем отдельно прошёл в Windows на Zig 0.15.2
в оптимизированном и sanitizer вариантах. Он проверяет production bind lambda,
переиспользование без admission/новых GPU-аллокаций и перенос владения между
материалами и тенями. Полный suite этим запуском не заменяется.

Реальная x86 GPU проверка арены

Сравнены два executable, различающиеся только этим участком world_renderer.h:
замороженный вариант до исправления и текущий. Использованы текущий клиентский
кэш ArgentTournamentDungeon, production WorldRenderer/NativeStore и 16 мешей,
снятых с настоящих загруженных mesh pages. Сумма данных — 45 608 байт.
Включён memory-pressure режим, shadow cache cap=32 МиБ. Для адресной
фрагментации использованы настоящие MEM_RESERVE/PAGE_NOACCESS размещения
в собственном 32-битном процессе. Игра не запускалась.

Бэкенды: native D3D9 и DXVK, GPU RTX 4090. По три измеряемых кадра на случай:

1. Около 942 МиБ свободно, крупнейший блок 60..66 МиБ.
   До: 0/16 резидентных мешей; 45 608 байт каждый кадр идут через bulk.
   После: 16/16 резидентны; первая загрузка 45 608 байт, затем 0 байт.

2. Около 942 МиБ свободно, крупнейший блок 12..15 МиБ.
   Обе версии отказывают резидентности и сохраняют все 16 draw через bulk.

3. Около 250 МиБ свободно, крупнейший блок 60..66 МиБ.
   Обе версии сохраняют отказ при недостатке aggregate reserve; все draw
   остаются через уже существующие bulk-буферы.

На всех 36 измеряемых кадрах R32F теневая картинка 128x128 побитово равна
эталону тех же мешей через bulk, включая 1 047 покрытых пикселей. Это проверка
байтов, адресации и сохранности геометрии; исходных игровых draw/поз/боя нет.
Ускорение полного кадра, прирост игрового FPS и устранение всех фризов
не измерялись. Размерные проверки не устраняют само давление/фрагментацию VA.
