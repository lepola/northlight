Findings and fixes

1. The reported symptom is a stale scene remaining over the moving camera while
   the UI continues updating. Full-size offscreen draws passed beforeDraw's
   orthographic UI gate after world capture. That gate marked the HDR boundary
   and ran renderEffects before hdrDraw's stricter backbuffer check. Consequently
   an offscreen image could replace the HDR world and close the frame's capture.
   The log has 2,229 Resources lines with FP16 format 113, interleaved with the
   logical format 22 used by hdrBegin. The first run starts at frame 21279 and
   coincides with the first logical scene copy after UI. This is consistent with
   the wrong boundary, but the log does not identify each render-target pointer
   or prove that every observed visual freeze has this cause.

   Fixed the target checks for fixed, orthographic, stock and learned UI paths.
   Stock/learned HDR boundaries also require safe texture inputs. renderEffects
   itself rejects foreign HDR targets. Existing stock SDR admission is retained.
   A production-method regression reproduces the former offscreen admission,
   then verifies that the subsequent real UI still consumes the current scene.

2. There are 538 sampled bounds records with valid > total. At the end, total=151
   and valid=196 produced unbounded=4294967251. Under memory pressure uploadReplay
   truncated/recycled the packet list while the bounds worker still borrowed its
   constant banks. Besides the lifetime violation, apply() rejected all remaining
   bounds because the job and packet counts no longer matched. At the sampled
   PointShadow peak (6.814 ms, frame 165735), the nearby bounds report likewise
   shows 289 valid for 246 packets and every retained packet unclassified.

   Join the bounds worker before truncating or recycling packets. This preserves
   current bounds on the surviving prefix and keeps the job's log counts coherent.
   The regression fails on the old ordering and checks destruction/recycling only
   after the join, for both ordinary and quarantined packets, across three upload
   cache/layout variants. The log alone cannot quantify the resulting GPU saving.

3. Re-analysis identified subdivision as a remaining CPU spike: 210 sampled stage
   records average 0.623378 ms, maximum 4.617 ms at device 2/frame 155194, with two
   WMO builds. The peak model record is 3.0265 ms at frame 125222. These are sampled
   build records, not costs paid on every frame.

   Use a local standard monotonic memory resource for the two temporary hash maps
   and one insertion lookup for a new vertex. The maps are discarded together at
   build completion. Geometry budgets, subdivisions, vertex/index order, seams,
   skin influences, padding, height sampling and GPU attributes remain unchanged.
   The dense test uses seven scratch allocations, peaks at 2,015,960 bytes and
   retains zero scratch bytes. All equivalence cases stay below 4 MiB scratch.

   Paired O2 CPU medians (13 alternating rounds, first three discarded):
     WMO grid:  3.065962 -> 2.419250 ms (21.1% less)
     WMO seams: 4.564737 -> 3.327400 ms (27.1% less)
     Model:     4.732113 -> 4.365613 ms (7.7% less)
   These are isolated build microbenchmarks, not an in-game FPS measurement.
